Act as a Principal Software Architect, AI Agent Engineer,
Knowledge Management Architect, and GitHub Copilot

TASK
Build a production-quality, reusable GitHub Copilot
Agent Skill named "team-knowledge-extractor".

Create it under:
.github/skills/team-knowledge-extractor/

This skill will extract engineering knowledge from
historical GitHub Copilot development sessions,
including sessions that span multiple repositories
and technologies.

It must work with the available GitHub Copilot
environments in VS Code and IntelliJ.

CONTEXT
The extraction process must support engineering
projects involving Spring Boot, Terraform, Azure
Databricks, Python packages, Azure integrations,
CI/CD pipelines, and other technology stacks.

Historical sessions may contain architectural
decisions, implementation corrections, and lessons
that are not captured in current source code.

The goal is to convert supported findings into
verified, reusable engineering procedures and
eventually into shared Agent Skills.

The developer experience must be extremely simple:
invoke one skill, wait for analysis, review a concise
report, and approve sharing if appropriate.

Do not require developers to learn SQL tools, agent
orchestration, evidence schemas, or multiple prompts.

SECTION A — SESSION HISTORY EXTRACTION

1. Use the native session_store_sql tool where
   available to retrieve historical session turns.

2. Discover the actual available tool interface.
   Do not invent SQL schemas, tool names, fields,
   table structures, or unsupported functionality.

3. Retrieve the complete accessible conversation,
   including user prompts and Copilot responses.

4. Support long sessions through batched retrieval.
   Track session identity, turn identifiers,
   retrieval boundaries, coverage, and gaps.

5. Preserve the chronology of:
   - Initial vague requirements
   - Requirement clarifications
   - Alternative designs considered
   - Architecture decisions and rationale
   - Implementation steps
   - Developer and architect corrections
   - Failed implementations and debugging
   - Changes to libraries or frameworks
   - Testing and Sonar remediation
   - Security and authentication decisions
   - Deployment and operational issues
   - Final decisions and outstanding problems

6. Do not rely only on compacted chat summaries.
   Use historical turns as evidence.

7. If a portion of history is inaccessible,
   explicitly report the gap. Never claim complete
   retrieval without verifying available coverage.

8. Support sessions involving multiple repositories.
   Map each significant finding to the correct
   application, repository, module, and revision.

SECTION B — SOURCE CODE VERIFICATION

Inspect relevant repositories, source code, Git
history, documentation, tests, dependencies,
configuration, and CI/CD definitions.

Use other repositories as read-only references.

Correlate conversation claims against actual code.

Distinguish:
- What someone requested
- What Copilot proposed
- What was actually implemented
- What was later changed
- What is currently present
- What was tested
- What remains unverified

Never assume that the final conversational answer
represents the final implementation.

Never assume the most recent implementation is
automatically the best engineering practice.

SECTION C — ENGINEERING KNOWLEDGE PRIORITIES

Investigate all relevant technologies dynamically,
without assuming the session is Java-only.

Give special attention to:

1. SHARED AND CENTRAL LIBRARIES
   Identify internal library coordinates, versions,
   version-management sources, interfaces, methods,
   configuration, dependency injection, and usage.

   Reconstruct exactly HOW libraries are used,
   not merely whether they are imported.

   Identify approved examples and alternatives.
   Do not infer approval merely from usage frequency.

2. AUTHENTICATION AND AUTHORIZATION
   Reconstruct actual authentication sequences:
   credential source, approved library, secret
   retrieval, token generation, token caching,
   expiry, downstream invocation, errors, security
   context, and validation where applicable.

   Capture call ordering and exact library APIs
   using source references, without exposing secrets.

   Distinguish service-to-service authentication,
   interactive authentication, and other patterns.

3. EXCEPTION HANDLING
   Identify shared exception libraries, exception
   hierarchies, propagation, translation, API error
   mapping, retry decisions, logging, and recovery.

   Distinguish technical failures from business
   failures and retryable from non-retryable cases.

4. SONAR AND CODE QUALITY
   Extract quality gates, rules, actual remediation
   techniques, security findings, code-smell fixes,
   and behavioral-regression safeguards.

5. TESTING AND COVERAGE
   Identify JUnit, Mockito, JaCoCo, Sonar, pytest,
   notebook tests, Terraform checks, and other
   applicable verification mechanisms.

   Investigate applicable coverage targets, including
   90% thresholds where specified or enforced.

   Determine the actual enforced coverage metric:
   line, branch, instruction, overall, or new-code.

   Record measured coverage, configured thresholds,
   exclusions, test reports, and their evidence.

   Never equate a stated 90% target with verified
   achievement. Unknown must remain unknown.

   Prefer meaningful behavioral testing over tests
   written only to increase coverage percentages.

6. ARCHITECTURE AND INTEGRATION
   Capture design patterns, data flows, interfaces,
   external APIs, storage, security boundaries,
   configuration, resilience, and dependencies.

7. AZURE, TERRAFORM, AND DATABRICKS
   When applicable, capture central Terraform
   modules, state management, CI/CD, Azure services,
   notebook orchestration, Python wheel packaging,
   jobs, data transformations, and operational rules.

8. HISTORICAL ENGINEERING LESSONS
   Recover errors, corrections, regressions,
   architectural pivots, rejected alternatives,
   temporary workarounds, and proven resolutions.

SECTION D — CRITICAL DEVIATION POLICY

A deviation from a common or centrally recommended
pattern must NEVER automatically be called wrong.

Investigate:
- What established baseline was being departed from
- Why the alternative was selected
- Whether the shared library lacked required features
- Whether legacy compatibility required the change
- Whether an incident or defect motivated it
- Whether security or performance justified it
- Whether approval or an exception exists
- Whether compensating controls were implemented
- Whether the solution was temporary or permanent
- Whether the alternative subsequently became preferred

Classify deviations as:
- Approved exception
- Justified alternative, approval unverified
- Unexplained variation
- Potential improvement
- Confirmed noncompliance
- Known defect
- Historical workaround
- Superseded design

Use "confirmed noncompliance" only when an
authoritative requirement and contrary behavior
are both supported by evidence.

Preserve valuable alternative implementations.
They may reveal gaps in our central libraries.

Never silently normalize differences.

SECTION E — PARALLEL ANALYSIS

Use native #useSubAgents / available subagent
delegation for substantial, independent analysis.

Suggested specialists:

Agent 1: Architecture and integration patterns
Agent 2: Shared libraries, authentication, exception
         handling, code quality, testing, and CI/CD
Agent 3: Historical decisions, failures, corrections,
         deviations, and reusable lessons

Provide each subagent with the relevant extracted
evidence and repository references explicitly.

Do not assume subagents inherit full chat history.

Require evidence-backed output, separate reports,
and independent conclusions.

The parent agent consolidates findings, resolves
duplicates, and reports genuine contradictions.

If delegation is unavailable, perform the analysis
sequentially and disclose that limitation.

Never claim subagents ran unless they actually did.

SECTION G — FINDING CLASSIFICATION

Keep these independent dimensions separate:

Evidence confidence:
verified / corroborated / inferred / unknown

Normative status:
approved-standard / observed-practice /
approved-exception / candidate /
confirmed-noncompliance / known-defect /
historical-only / unresolved

Reuse scope:
team-wide / technology-specific /
project-specific / not-recommended

Recommendation:
create-skill / update-skill / merge-skill /
keep-existing / retire-skill / permanent-instruction /
reference-document / automated-check /
no-action / needs-review

Approval:
pending / approved / rejected /
approved-with-conditions

A code occurrence is not policy approval.
A passing build is not sufficient proof of
runtime correctness.
A missing Sonar report is UNKNOWN, not failed.

Read-only against applications, repositories,
