SECTION A — AUTOMATIC REPOSITORY DISCOVERY

On invocation:

1. Identify the intended repository or project
   from the currently selected workspace context.

2. Discover its technology stack automatically.

3. Detect multiple modules, applications, packages,
   infrastructure components, and linked repositories.

4. Separate the main application from centrally
   maintained library or reference repositories.

5. Identify application entry points, execution paths,
   dependencies, configuration and build systems.

6. Inspect repository history and existing documentation
   where available.

7. Record the exact repository revision analyzed.

8. Avoid assuming every workspace folder belongs
   to the same application.

9. Treat external reference repositories as read-only.

10. If scope is truly ambiguous, ask one concise
    question; otherwise proceed automatically.

SECTION B — ARCHITECTURE RECONSTRUCTION

Reconstruct how the application actually works.

Investigate:
- Business purpose and application responsibilities
- Modules and component boundaries
- Controllers, services, repositories and workers
- Batch jobs, schedulers and event-driven processing
- Input/output flows and external dependencies
- API contracts and downstream systems
- Persistence, transactions and data movement
- Configuration and environment differences
- Dependency injection and abstraction boundaries
- Authentication and authorization
- Exception handling, retries and recovery
- Logging, metrics and observability
- Performance, concurrency and scalability
- Packaging and deployment architecture
- Tests, build checks and quality gates

Produce an evidence-backed execution-flow description.

Do not invent business requirements, architectural
rationale, or historical decisions from code alone.

Distinguish directly observed behavior from inferred
intent and unresolved questions.

Give highest priority to identifying:

5. Testing practices and 90% coverage requirements
6. Central configuration and secret management

SECTION E — DEVIATIONS AND EXCEPTIONS

A different implementation is NOT automatically wrong.

Before identifying any deviation as a problem:

1. Establish whether an authoritative baseline exists.
2. Identify the exact observed difference.
3. Search documentation and Git history for rationale.
4. Determine whether the alternative solves a
   limitation, compatibility problem, security issue,
   performance constraint, or production incident.
5. Identify compensating safeguards.
6. Examine evidence that the alternative works.
7. Determine whether it is approved, tolerated,
   experimental, or unresolved.
8. Preserve valuable alternatives for architect review.

Never label a difference as noncompliance merely
because most other projects use another approach.

Never treat commonly repeated code as proof
of an approved standard.

Never automatically recommend replacing custom
implementations with central libraries without
checking functional compatibility.

A deviation may reveal a valuable improvement
that should be proposed to the central library team.

SECTION F — GIT HISTORY AND ENGINEERING EVOLUTION

Investigate meaningful Git commits, branches,
diffs and available change documentation.

Identify:
- Important architectural refactorings
- Dependency and library replacements
- Authentication implementation changes
- Sonar remediations
- Test coverage improvements
- Incident and defect fixes
- Regressions and corrections
- Changes in deployment patterns
- Removed or replaced approaches

Do not claim to know why a change occurred
unless commit messages, documents, tests or other
accessible evidence support that explanation.

If the reason is unclear, record an architectural
question for the developer or architect.

If Git history is shallow or unavailable,
report the limitation.
