SECTION C — DEVIATIONS ARE NOT AUTOMATIC DEFECTS

This is a mandatory architectural principle.

A deviation from a common implementation is NOT
automatically bad, incorrect or noncompliant.

Before recommending standardization, examine:

- The original engineering requirement
- The relevant central standard, if one exists
- The actual differences
- The reason for the alternative
- Constraints at implementation time
- Shared library limitations
- Backward compatibility requirements
- Security, operational or performance needs
- Production incidents or historical defects
- Approval evidence
- Compensating controls
- Test and production evidence
- Current applicability

Treat these as distinct outcomes:

APPROVED EXCEPTION
A formally authorized alternative implementation.

JUSTIFIED ALTERNATIVE
Evidence supports its use, but approval is
unknown or still needs confirmation.

UNEXPLAINED VARIATION
Different implementation with insufficient
evidence to classify as correct or incorrect.

POTENTIAL IMPROVEMENT
An alternative that may improve the shared
standard or central library.

CONFIRMED NONCOMPLIANCE
Both an authoritative standard and a violation
are established by evidence.

KNOWN DEFECT
An independently established implementation
problem.

HISTORICAL WORKAROUND
A context-dependent solution that should not
automatically become a general pattern.

Never infer that the majority approach is correct
simply because it appears in more repositories.

Never penalize justified architectural exceptions.

Where multiple legitimate patterns exist,
preserve their applicability conditions and
decision criteria.

Architectural disagreements requiring judgment
must be escalated for architect review.

SECTION D — GOLDEN REFERENCE IMPLEMENTATIONS

Identify the strongest candidates for approved

A golden reference should demonstrate:
- Correct shared library usage
- Compliance with relevant architectural standards
- Clear, maintainable implementation
- Appropriate exception handling
- Security and authentication correctness
- Relevant test coverage and test quality
- Production suitability where established
- Documented limitations and applicability
- Approval from responsible architects

Distinguish candidate references from approved ones.

Maintain a catalog of golden implementations.

Reference:
- Repository
- Module
- Class/function
- Relevant methods
- Framework and library versions
- Commit or revision
- Required configuration
- Applicability boundaries
- Approval owner and status

Do not copy proprietary code unnecessarily into
skills. Prefer linking to approved internal references.

A future Copilot agent should be able to understand
exactly which implementation to study and why.

SECTION F — EXISTING SKILLS INVENTORY

Before recommending or generating anything,
inventory the current team skills repository.

For every existing skill identify:
- Name and description
- Purpose and activation trigger
- Applicability and technology
- Supporting evidence
- Dependencies and references
- Current version
- Maintainer and approval status
- Validation status
- Known limitations
- Overlap with other skills

Each new candidate must receive one disposition:

CREATE
New procedure with sufficient value and evidence.

UPDATE
Improve an existing skill with new verified knowledge.

MERGE
Combine overlapping skills with compatible purposes.

KEEP
Existing skill remains appropriate.

RETIRE
Remove or deprecate an obsolete or misleading skill
through an approved change process.

NEEDS REVIEW
Insufficient evidence or unresolved architectural
disagreement prevents standardization.

Do not continuously generate nearly identical skills.

SECTION G — SEPARATE KNOWLEDGE TYPES

Determine whether each finding should become:

A. AGENT SKILL
Repeatable task-oriented procedure with activation
conditions, inputs, steps, validation and outputs.

B. PERMANENT COPILOT INSTRUCTION
A broadly applicable engineering convention,
restriction or requirement.

C. REFERENCE DOCUMENT
Detailed architecture, implementation examples,
library usage, historical decisions and explanations.

D. AUTOMATED CHECK
A deterministic rule better enforced through tests,
Sonar, CI, static analysis or build validation.

E. APPLICATION-SPECIFIC KNOWLEDGE
Business rules or configuration that should remain
within the owning application.

F. ARCHITECTURAL REVIEW ITEM
Unresolved decisions, inconsistent standards or
potential improvements needing team approval.

Do not generate an Agent Skill for something that
would be better implemented as a deterministic check.

Do not hardcode individual application's business
rules into global engineering skills.

SECTION H — SKILL PRIORITIZATION

Rank proposed skills using:
- Reusability across applications
- Engineering impact
- Reliability of supporting evidence
- Relevance to team standards
- Frequency of future use
- Risk reduction
- Developer time savings
- Ease of validation
- Maintenance burden
- Potential overlap with existing skills

Provide an explainable score or tier and rationale.

Recurring evidence from multiple repositories
should increase confidence when comparable.

However, one excellent and approved implementation
may justify a valuable skill if its procedure is
clearly reusable.

Do not make a minimum repository count an
absolute requirement for every skill.

Keep SKILL.md focused.

SECTION K — INDEPENDENT SKILL VALIDATION

Every generated or modified skill must be evaluated
before being recommended for team adoption.

Use independent reviewer subagents where helpful.

Validation must include:

1. SKILL.md structural and frontmatter validation
2. Broken reference checks
3. Compatibility with the canonical standards
4. No contradiction with existing approved skills
5. Correctness of library usage and examples
6. Accurate exception and alternative handling
7. Security and deployment safeguards
8. Applicability to more than one scenario
9. A realistic fresh-session test case
10. A negative test or edge case

For example:
- Can an unfamiliar Java agent reproduce an approved
  authentication pattern without inventing methods?
- Can it preserve standardized exception handling?
- Can it identify the correct Sonar/coverage checks?
- Can a Terraform agent find the central module first?
- Can a Databricks agent understand notebook and
  Python wheel boundaries?
- Can it recognize a justified exception without
  automatically replacing it?

Where practical, compare a baseline task without
the skill to the same task with the skill.

Record expected behavior, observed behavior,
limitations and unresolved evaluation results.

Do not claim successful evaluation if the test
was not actually executed.
